19.1 · Warehouse kyun chahiye? godown vs dukaan

Socho ek badi retail chain hai. Har shop ke counter par billing software chal raha hai: customer aaya, item scan hua, bill bana. Ye software roz lakhon chhote-chhote insert/update karta hai. Isse kehte hain OLTP (Online Transaction Processing). Ye system abhi kya ho raha hai ke liye bana hai, aur fast aur safe (ACID) hona uski sabse badi zarurat hai.

Ab CEO ek sawaal puchta hai: “Pichhle 3 saal mein north zone mein kaunsi product category ki sale quarter-wise kitni rahi?” Agar ye query seedhe billing database par chala di, to: (1) crores rows scan honge, (2) billing slow ho jayegi, (3) alag-alag shops ka data alag formats mein hoga, (4) purana data to shayad delete ho chuka hoga.

Isliye company ek alag godown banati hai: Data Warehouse. Sab shops/systems ka data yahan saaf karke, jod ke, saalon ki history ke saath rakha jata hai, aur design aisa hota hai ki sum/average/group-by wale sawaal tez chalein. Is analysis ko kehte hain OLAP (Online Analytical Processing).

Ek line mein

Data warehouse = alag-alag sources ka data ek jagah, decision-making (analysis) ke liye, history ke saath, read-mostly design mein. Daily kaam (billing) ke liye nahi.

Shabdon ka matlab
  • ACID = transaction ki 4 safety properties (atomic, consistent, isolated, durable); abhi detail zaroori nahi.
  • Normalized (3NF/BCNF) = tables aise toote hue ki ek fact ek hi jagah likha ho (Lesson 10-11). Denormalized = jaan-boojh ke repeat karke tables jodna taaki join kam lagein.
  • Aggregate = SUM / AVG / COUNT jaisa function jo kai rows ko ek number mein badalta hai. Scan = table ki saari rows padhna.
GATE trap

Warehouse ko “normalized” mat samajhna. OLTP normalized hota hai (anomalies hataane ke liye); warehouse mein data update hota hi nahi, isliye anomaly ka darr nahi, aur joins kam karne ke liye denormalize karte hain. (Snowflake thoda normalized hota hai, par phir bhi OLTP jitna nahi.)

19.2 · Warehouse ki 4 properties (Inmon ki definition)

Bill Inmon ke according data warehouse hai: subject-oriented, integrated, time-variant, non-volatile data ka collection. Chaaron ko ek-ek karke samjho.

PropertyMatlab (simple)Example
Subject-orientedData topic/subject ke around organized (Sales, Customer, Product), application ke around nahi. Sirf analysis ke kaam ka data rakhte hain.Billing app ke 40 tables se sirf “Sales” subject ka data alag nikala.
IntegratedAlag sources ka data ek consistent format mein: naming, units, codes, data types same.Source A: gender = M/F, Source B: 1/0 → warehouse: Male/Female. Rupees vs Dollars → sab INR.
Time-variantData time ke saath rakha jata hai; history (5-10 saal) hoti hai; har record ke saath time element.Har sale ke saath date; customer ka purana address bhi bachta hai.
Non-volatileEk baar load hone ke baad data update/delete nahi hota (sirf naya load + read).Kal ki sale aaj edit nahi hoti; nayi sale bas append hoti hai.
Trap: non-volatile ka matlab

“Non-volatile” ka matlab ye nahi ki warehouse mein kabhi naya data nahi aata. Naya data periodically load hota hai (roz raat ko); par jo data ek baar aa gaya use in-place modify nahi karte.

Ab tum try karo

Q. Do sources mein “Delhi” ko “DEL” aur “New Delhi” likha hai; warehouse mein ek hi naam bana diya. Kaunsi property?

Ans: Integrated.

19.3 · Fact table aur Dimension table numbers vs descriptions

Warehouse ke har sawaal mein do tarah ki cheezein hoti hain:

  • Number jo hum jodna/average karna chahte hain: quantity, revenue, discount. Inhe measures (facts) kehte hain.
  • Jis angle se hum dekhna chahte hain: kab (date), kya (product), kahan (store), kisne (customer). Inhe dimensions kehte hain.

Analogy: Sales register ka ek line = “5 Jan ko, Pune store par, Galaxy phone, 2 piece, Rs 40,000”. Isme 2 aur 40,000 number hain (fact), baaki 5 Jan, Pune, Galaxy description hain (dimension).

Neela column = foreign keys (dimension ki taraf). Peela = measures (numbers).

Notation: PK, FK, key
  • PK (primary key) = row ko unique pehchanne wala column. DATE_DIM mein date_key PK hai.
  • FK (foreign key) = fact ke column jo kisi dimension ki PK se match karta hai. SALES_FACT ki row (1, 101, 11, 2, 40000): date_key = 1 → DATE_DIM ki 2026-01-05 wali row; product_key = 101 → Galaxy-M; store_key = 11 → Connaught (Delhi).
  • Measure = fact ka numeric column jise jodte/average karte hain: quantity = 2, revenue = 40000.

Query: “Category-wise, city-wise total revenue?”

SELECT p.category, s.city, SUM(f.revenue) AS total_rev
FROM   SALES_FACT f
JOIN   PRODUCT_DIM p ON f.product_key = p.product_key
JOIN   STORE_DIM   s ON f.store_key   = s.store_key
GROUP BY p.category, s.city;
  1. Fact ki har row ko uska product mil gaya (join) → category pata chali.
  2. Har row ko uska store mil gaya → city pata chali.
  3. Ab group karo: (Mobile, Delhi) = 40000 (row 1). (Mobile, Pune) = 80000 + 60000 = 140000 (rows 2 aur 4). (Laptop, Delhi) = 60000 (row 3).

Trap

Measure hamesha numeric aur aggregatable hota hai. Product ka naam, city, year = dimension attribute (labels), chahe wo numeric dikhe (jaise year = 2026, jise hum SUM nahi karte). Aur fact table mein sirf keys + measures, descriptions nahi (wo dimension mein).

19.4 · Grain ek row = exactly kya?

Grain = fact table ki ek row kis level of detail ko represent karti hai. Ye warehouse design ka pehla decision hota hai (grain → dimensions → measures).

  • Fine grain: “ek bill ki ek item line”. Sabse zyada detail, par rows bahut.
  • Coarse grain: “ek product, ek store, ek din ka total”. Rows kam, par neeche (detail) drill-down nahi ho sakta.
Rule

Fine grain se coarse bana sakte ho (roll-up). Coarse grain se fine kabhi nahi (information kho gayi). Isliye warehouse mein jitna ho sake atomic (finest) grain rakhte hain.

Grain se rows ka upper-bound

Agar grain = (date, product, store), to fact table ki maximum rows = (#dates) × (#products) × (#stores). Actual rows isse kam hoti hain jab sab combinations mein sale nahi hui (sparse).

Kaise? (formula ko letter-by-letter)

  1. Grain (date, product, store) ka matlab: fact ki har row ek (date, product, store) combination ka record hai.
  2. Maan lo 365 dates, 1000 products, 50 stores. Ek row = ek combination chunna; date ke 365 tareeke × product ke 1000 × store ke 50.
  3. Max rows = 365 × 1000 × 50 = 18,250,000 (N1 mein dekho). Actual isse kam, kyunki har combination par sale nahi hoti.

19.5 · Star schema sabse simple & sabse popular

Star schema: beech mein ek fact table; uske chaaron taraf ek-ek dimension table (flat, denormalized). Dikhne mein taara jaisa lagta hai, isliye naam.

Figure 19.1 - Star schema: ek fact table, chaaron taraf flat (denormalized) dimension tables. Orange rows = measures, PK/FK = keys.
  • Fact table ki primary key = (date_key, product_key, store_key, customer_key) (composite). Har part ek foreign key hai jo ek dimension ki PK se judta hai.
  • Dimension mein poori hierarchy ek hi table mein: STORE_DIM mein city, state, country saath-saath. Matlab “Pune” ke saath “Maharashtra, India” baar-baar repeat hoga (redundancy). Isi ko denormalized kehte hain; hum jaan-boojh ke ye karte hain.
  • Koi bhi query = fact ⋈ kuch dimensions (sirf ek level ka join). Isliye fast aur likhna aasan.
Star schema ke fayde

Kam joins (query fast), simple structure, tools/BI friendly. Nuksan: dimension mein redundancy → thoda zyada storage, aur update anomalies agar dimension badle (par warehouse mein updates kam hote hain).

19.6 · Snowflake schema dimension ko bhi normalize karo

Snowflake = star schema jisme dimension tables ko normalize karke chhoti-chhoti related tables mein tod diya jata hai (hierarchy ke levels alag tables). Fact table wahi rehta hai.

Figure 19.2 - Snowflake schema: dimension khud normalized hoke "snowflake" jaisi branches banati hai. DATE_DIM yahan flat chhodi gayi hai (sab dimension todna zaroori nahi).

Star mein: PRODUCT_DIM(product_key, name, brand, category_name, dept) — 10 lakh products ke saath category ka naam 10 lakh baar likha hua.
Snowflake mein: PRODUCT_DIM(product_key, name, brand, category_key) + CATEGORY_DIM(category_key, category_name, dept) — category ka naam sirf ek baar.

Yaad rakhne ka trick

Star = Simple, Speedy, redundant.   Snowflake = Space-saving, Slower (joins), Structured (normalized).

19.7 · Fact constellation (galaxy) schema

Jab ek hi warehouse mein ek se zyada fact tables hon, aur wo kuch dimensions share karein, to us design ko fact constellation ya galaxy schema kehte hain (kai stars ek-dusre se jude hue). Ye enterprise warehouse mein common hai (Sales, Shipping, Returns, Inventory ka alag-alag fact).

Figure 19.3 - Fact constellation (galaxy): do fact tables, kuch dimensions share karte hain (purple).

Shared dimensions ko conformed dimensions kehte hain: unka meaning aur keys sab facts ke liye same. Isse Sales aur Returns ko ek hi DATE/PRODUCT par compare kar sakte ho (“kitna becha vs kitna wapas aaya”).

SchemaFact tablesDimensionsPehchaan
Star1Har ek flat, direct fact se jud-tiTaara
Snowflake1Kuch dimensions aage normalized sub-tables meinBranches wala taara
Galaxy / constellation2 ya zyadaKuch dimensions facts ke beech sharedKai taare jude hue
GATE trap

Snowflake ka fact table ek hi hota hai; “do fact tables share dimension” sunte hi constellation likho. Aur snowflake mein fact table normalize nahi hota; sirf dimensions hote hain.

Ab tum try karo

Q1. SALES_FACT aur INVENTORY_FACT dono DATE_DIM, PRODUCT_DIM use karte hain. Schema?
Q2. STORE_DIM ko CITY_DIM mein tod diya. Ab “country-wise revenue” ke liye kitne joins (fact se CITY_DIM tak)?

Ans: Q1 Fact constellation. Q2 Fact⋈STORE_DIM⋈CITY_DIM = 2 joins (star mein sirf 1).

19.8 · Surrogate key kam important

Surrogate key = dimension table ki artificial integer ID (1, 2, 3, ...) jo warehouse khud banata hai aur fact table mein foreign key ban ke aati hai. Business ki asli ID (jaise C-8841) natural key hai. Surrogate isliye, kyunki alag sources ke IDs alag ho sakte hain aur integer chhota/fast hota hai.

Syllabus mein nahi — skip

ETL pipeline, SCD types, data mart / enterprise warehouse ke prakaar, fact table ke types: ye sab GATE DA syllabus ke bahar hain. Bas itna pata ho ki data sources se saaf (clean) karke warehouse mein load hota hai.

19.9 · GATE-style numerical aur PYQ is lesson ka

PYQ status

GATE DA 2024, 2025, 2026 ke papers mein schema-type (star/snowflake) par koi seedha sawaal nahi aaya. Data-warehouse ke 3 sawaal aaye jo Lesson 20 mein diye hain (2026 Q18, 2026 Q43, 2025 Q46). Isliye yahan standard numerical practice hai (answers derived).

N1. Grain se maximum fact rows

Daily grain: 365 din × 1000 products × 50 stores. Maximum rows? Agar har din har store par sirf 10% products bikte hain?

Solution: max = 365 × 1000 × 50 = 18,250,000. 10% = 1,825,000 rows (sparse fact table).

N2. Snowflake se storage bachat

PRODUCT_DIM mein 10 lakh rows; category name 20 byte, 50 distinct categories, key 4 byte. Star mein har row mein name; snowflake mein har row mein 4-byte category_key + alag CATEGORY_DIM(key 4B, name 20B).

Solution: star: 1,000,000 × 20 = 20,000,000 B. Snowflake: 1,000,000 × 4 = 4,000,000 B plus CATEGORY_DIM 50 × (4+20) = 1,200 B ⇒ 4,001,200 B. Bachat = 15,998,800 B ≈ 16 MB. (Fact table ke saamne ye choti bachat hai — isliye star hi default hai.)

N3. Joins gino

“Country-wise, year-wise revenue.” Star mein STORE_DIM (country andar) aur DATE_DIM. Snowflake mein STORE_DIM → CITY_DIM (country wahan) aur DATE_DIM flat.

Solution: Star: fact⋈STORE_DIM, fact⋈DATE_DIM = 2 joins. Snowflake: fact⋈STORE_DIM, STORE_DIM⋈CITY_DIM, fact⋈DATE_DIM = 3 joins.

19.10 · Practice questions 12, answers ke saath

1. (MCQ) Kaun-sa warehouse ki property nahi hai? (a) subject-oriented (b) volatile (c) time-variant (d) integrated
✔ (b) volatile
Sahi property non-volatile hai.
2. SalesAmount aur CustomerName mein se measure kaun?
✔ SalesAmount
Numeric aur aggregatable; CustomerName descriptive attribute (dimension).
3. Fact table ka primary key typically kaisa hota hai?
✔ Composite key (dimension foreign keys ka combination, grain ke hisaab se)
4. (MCQ) Do fact tables DATE_DIM aur PRODUCT_DIM share karte hain. Schema?
✔ Fact constellation (galaxy)
5. (MSQ) Star ke comparison mein snowflake ke bare mein sahi: (a) zyada joins (b) kam redundancy (c) fact table normalize hota hai (d) dimension normalized
✔ (a), (b), (d)
(c) galat: fact table normalize nahi hota, dimensions hote hain.
6. Grain: 200 din × 500 products × 20 stores. Max fact rows?
✔ 200 × 500 × 20 = 2,000,000
7. Star schema mein ek hi dimension (STORE_DIM) mein city, state, country saath-saath hain. Isse kya fayda aur kya nuksan?
✔ Fayda: fact se sirf 1 join (query fast). Nuksan: city → state, state → country FD ki wajah se redundancy (dimension 3NF mein nahi). Ye intentional denormalization hai.
8. OLTP ya OLAP: “pichhle 5 saal mein region-wise average order value”.
✔ OLAP
Historical, aggregate, read-only.
9. Snowflake mein STORE_DIM ko CITY_DIM mein tod diya. Country-wise revenue ke liye fact se country tak kitne joins? Star mein?
✔ Snowflake: 2 (fact ⋈ STORE_DIM ⋈ CITY_DIM). Star: 1.
10. Star schema mein STORE_DIM(store_key, city, state, country) redundant kyun hai?
✔ Ek state ke saare cities mein state/country repeat hota hai (functional dependency city → state, state → country, par key store_key); isliye dimension 3NF mein nahi. Ye intentional denormalization hai.
11. Grain (date, product, store) se (month, product, store) karne par fact rows badhengi ya ghategi?
✔ Ghategi (coarse grain, kam rows)
Fine grain se roll-up possible hai, coarse se drill-down nahi.
12. (MCQ) Fact table ke bare mein galat: (a) narrow aur lambi (b) numeric measures (c) har row mein long descriptive text (d) dimensions ki FKs
✔ (c)
Descriptive text dimension table mein rehta hai.
Lesson 19 cheat box
  • Warehouse = subject-oriented, integrated, time-variant, non-volatile.
  • OLTP: current, normalized, small updates, ACID. OLAP: historical, denormalized, big read-only aggregates.
  • Fact = measures + FKs (grain decide karta hai row ka matlab). Dimension = descriptive attributes + surrogate PK.
  • Star: 1 fact + flat dims (fast, redundant). Snowflake: normalized dims (space, more joins). Galaxy: ≥2 facts share dims.
  • Max fact rows = product of distinct values of grain dimensions.
  • Surrogate key = dimension ki artificial integer PK, fact mein FK.
