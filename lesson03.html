Diagram se table kyun?

ER diagram insaano ke liye hai; DBMS ko tables chahiye. ER → tables ek mechanical process hai: har cheez ko ek rule se table ya column bana do. Rules yaad ho gaye to koi bhi ER diagram 2 minute mein tables ban jaata hai — aur “kitni tables?” sawaal ek formula ban jaata hai.

3.1 · Strong entity vs Weak entity jiski apni pehchaan nahi

Kahani se samjho

Company ke har employee ke dependents (bachche, pati/patni) ka record rakhna hai. Dependent ka sirf ek naam hai (“Riya”) — par company ke 5 alag employees ki beti ka naam Riya ho sakta hai! Sirf “Riya” se kaunsi Riya, ye pata nahi. (Employee E1, Riya) bolne par hi pehchan banti hai. Matlab Dependent apni pehchan ke liye owner (EMPLOYEE) par nirbhar hai — yehi weak entity hai.

  • (E1, Riya) aur (E2, Riya) dono allowed — alag owners. (E1, Riya) do baar nahi — full key unique honi chahiye.
  • Partial key sirf ek owner ke andar unique hoti hai (E1 ke dependents ke beech DepName unique).
  • Agar E1 ke do bachchon ka naam Riya hai, to DepName partial key ban hi nahi sakta — koi aur discriminator (DepNo) chuno.
Weak entity kab banti hai, kab nahi?
  • Weak entity ke liye teen cheezein: (1) apni key nahi; (2) ek owner entity; (3) owner se identifying relationship, jo 1:N ho (owner 1, weak N) aur weak side total.
  • Agar DEPENDENT ke paas khud ki unique DependentID hai, to wo strong entity hai (chahe EMPLOYEE se juri ho). Sirf juda hona = weak nahi.
  • Weak entity ki kai owners bhi ho sakti hain (kai identifying relationships) — tab key = sab owners ki keys + partial key.
  • Weak entity ke apne bhi weak entity ho sakte hain (multi-level): BUILDING → ROOM → SEAT. Seat ki key = (BNo, RNo, SNo).
Ab tum try karo

Q. COURSE(CID key). SECTION(SecNo, Semester) ek course ke andar SecNo se pehchana jaata hai. SECTION ki key kya, aur kya wo weak hai?

Answer: SECTION weak hai; partial key = SecNo (ya SecNo + Semester, jo bhi owner ke andar unique kare); full key = (CID, SecNo) [ya (CID, SecNo, Semester)].

3.2 · Specialization, Generalization, Aggregation Enhanced ER (EER)

Kabhi kabhi ek entity type ke kuch entities ki alag khaas properties hoti hain. PERSON ke andar STUDENT (RollNo, CGPA) aur TEACHER (Salary) hain. Poore PERSON ko do tables mein todne ke bajaye hum sub-type banate hain.

Specialization
top-down: PERSON → STUDENT, TEACHERGeneralization
bottom-up: STUDENT, TEACHER → PERSON

Dono ek hi diagram hain, bas dekhne ka rasta alag. Superclass ke saare attributes aur relationships subclass ko inherit hote hain (“IS-A” relation: student is a person).

ConstraintMatlabSymbol
Disjoint (d)Ek entity sirf ek subclass meincircle mein d
Overlapping (o)Ek entity kai subclass mein ho sakti hai (student bhi, teacher bhi)circle mein o
TotalSuperclass ki har entity kisi subclass mein zaroorDouble line superclass se
PartialKuch superclass entities kisi subclass mein nahisingle line
(a) Disjoint + Total: har PERSON exactly ek: STUDENT ya TEACHER
(b) Overlapping + Partial: koi dono bhi ho sakta hai, koi dono nahi
  • Subclass ke paas superclass ki key hi hoti hai (apni nayi key nahi). Subclass ke local attributes alag (CGPA sirf STUDENT ka).
  • Do kism ke 4 combos: d/o × total/partial.
  • Aggregation: ek relationship ko hi ek entity ki tarah maan kar kisi aur entity se jodna. Example: EMPLOYEE works_on PROJECT (ye ek unit), aur MANAGER us unit ko monitors karta hai. Ye tab chahiye jab “relationship ka relationship” chahiye aur ternary sahi na baithe. Table mein: MONITORS(EmpID, ProjID, MgrID) — jahan (EmpID, ProjID) WORKS_ON ka key hai (FK).
Trap

ISA ki direction: triangle/circle ka nok superclass ki taraf. Subclass entity automatically superclass ki entity bhi hai — STUDENT ki har entity PERSON ki bhi entity hai (same Pid).

Table-count mantra

Entities (strong + weak) + multivalued attributes + M:N relationships + n-ary relationships − (1:1 total-total merges). 1:N aur identifying relationships ke liye 0 extra tables.

“Minimum” ka matlab

Question mein jab “minimum number of tables/relations” ho, to hum sabse compact valid design maante hain: FK (NULL-able bhi) se kaam chalao, relationship ke liye alag table sirf tab jab zaroorat ho (M:N, n-ary). Agar kaha ho “each relation in 3NF” to ek aur check: koi table dependency-galat na ho (2NF/3NF violation) — Lesson 10-12 mein.

3.6 · Rules 3, 4, 5: Binary relationships 1:1, 1:N, M:N

Rule 3 — 1:1

Ek hi side mein doosri ki FK kaafi hai. Kis side? Jis side ki participation total ho (tab FK kabhi NULL nahi hogi). FK par UNIQUE lagao (1:1 enforce karne ke liye).

Example: EMPLOYEE (0,1) — MANAGES — (1,1) DEPARTMENT (har department ka exactly ek manager; employee manager ho bhi sakta hai, nahi bhi).

3.7 · Rules 6, 7 & unary relationships

Rule 6 — Multivalued attribute (dobara, ek aur example)

EMPLOYEE(EmpID, Name, {Skill}) → EMPLOYEE(EmpID, Name) + EMP_SKILL(EmpID FK, Skill). Har multivalued attribute ke liye ek table — do multivalued ho to do tables (ek mein dono mat rakho, wo spurious combinations banata hai: 3 skills × 3 phones = 9 rows!).

Unary (recursive) relationship

Rule wahi, bas dono “entities” same hain:

  • Unary 1:N (SUPERVISES): FK ussi table mein khud ko refer kare. Koi nayi table nahi.
  • Unary M:N (prerequisite): bridge table mein dono columns same entity ki key (roles ke naam se rename).

3.9 · Minimum tables: counting method GATE ka favourite

Recipe (5 steps)

  1. Entities: har strong entity = 1; har weak entity = 1.
  2. Multivalued attributes: har ek = +1 (composite multivalued bhi sirf +1).
  3. Relationships: M:N = +1; ternary/n-ary = +1; unary M:N = +1. 1:N, unary 1:N, identifying, derived, composite = 0.
  4. 1:1 ke liye merge: har 1:1 jahan dono side total ho = −1 (dono entities ek table). Baaki 1:1 = 0.
  5. Specialization: question ke hisaab se (3.8).
CheezTables ka effect
Strong / weak entity+1 each
Multivalued attribute (simple ya composite)+1 each
Composite / derived attribute0
1:N, N:1 (binary ya unary)0 (FK)
1:1 (koi bhi participation)0 (FK)
1:1, dono total−1 (merge)
M:N (binary ya unary)+1
Ternary / n-ary+1
Identifying relationship0

Worked examples

C1. E1, E2, E3 strong; E1–E2 M:N, E2–E3 1:N (E3 is N-side), E1 mein multivalued attribute. Minimum tables?
✔ 5
Entities 3 + multivalued 1 + M:N 1 + (1:N) 0 = 5.
C2. A, B strong, 1:1 R, dono total; B ka ek multivalued attribute; C weak entity jiska owner B hai. Minimum tables?
✔ 3
Formula: 2 strong + 1 weak + 1 multivalued − 1 (1:1 both total merge) = 3. Tables: AB (merged), B_MULTI, C.
C3. EMPLOYEE, DEPARTMENT, PROJECT strong. WORKS_FOR (EMP N : DEPT 1), WORKS_ON (EMP M : PROJECT N), MANAGES (EMP 1 : DEPT 1; DEPT total, EMP partial). Employee ka {Skill} multivalued. Minimum tables?
✔ 5
3 entities + {Skill} 1 + WORKS_ON (M:N) 1 = 5. WORKS_FOR 0, MANAGES 0 (FK in DEPARTMENT, 1:1 but only one side total ⇒ no merge).
C4. Entity E strong with composite Address(Street, City), derived Age, and two multivalued attributes {Phone} and {Email}. Relationship: ternary R between E, F, G (all strong). Minimum tables?
✔ 6
E, F, G = 3; Phone +1, Email +1 = 5; ternary R +1 = 6. Address, Age = 0.
C5. EMPLOYEE unary SUPERVISES 1:N, unary MARRIED_TO 1:1, and unary FRIEND M:N. Minimum tables?
✔ 2
EMPLOYEE (1); SUPERVISES, MARRIED_TO: FK in same table (0); FRIEND M:N: +1. Total 2.

3.11 · Poora case study: University ER se tables tak, ek baar mein

Requirement: Student (RollNo, Name, {Phone}) ek Department mein major karta hai (N:1). Instructor (IID, IName) ek department mein kaam karta hai (N:1). Course (CID, Title) ke kai Sections hote hain; Section ki pehchan (CID, SecNo) se hai, Year section ka attribute (weak). Student sections mein enroll hota hai (M:N, attribute Grade). Har section ko ek instructor padhata hai (INSTRUCTOR 1 : SECTION N).

Fig 3.3 — University ER (SECTION weak entity of COURSE; double diamond HAS_SECTION)

Step by step

  2. Multivalued Phone → STUDENT_PHONE (6).
  3. M:N ENROLLS → ENROLLS bridge (7).
  4. N:1 MAJORS_IN, WORKS_IN → FK DeptID in STUDENT, INSTRUCTOR (0 extra). 1:N TEACHES → FK IID in SECTION (0 extra). HAS_SECTION identifying → 0 extra.

3.10 · PYQ — GATE DA 2026 Q61 (NAT, 2 marks)

Q.61  Consider an ER model with the entities E1(A11, A12, A13) and E2(A21, A22, A23), where A11, A12, A13 are the attributes of E1, and A21, A22, A23 are the attributes of E2. Let A22 be a multi-valued attribute. A11 and A21 are the primary keys of E1 and E2, respectively.
Let R12 be a many-to-many relationship between E1 and E2. Participation of both E1 and E2 in R12 is total.
The minimum number of relations required to convert the ER model into relational model (assuming there is no other functional dependency) where each relation is in third normal form (3NF) is __________. (Answer in integer)
  1. E1 (strong, A11 key): E1(A11, A12, A13) — 1 relation.
  2. E2 (strong, A21 key): single-valued attributes A21, A23 → E2(A21, A23) — 1 relation. (A22 multivalued, ye main table mein nahi.)
  3. A22 multivalued: E2_A22(A21, A22) with A21 FK — 1 relation (rule 6).
  4. R12 (M:N): R12(A11, A21) — 1 relation (rule 5).
  5. Total participation → sirf NOT NULL / existence constraint; extra relation nahi. M:N par total hone se bhi dono side “kai” rehta hai, isliye bridge table chhoot nahi sakti.
E1+E2(A21, A23)+E2_A22+R12

✔ Answer: 4  (handbook ke official answer ke saath mel khaata hai; derivation independent hai)

Trap: total participation se table kam nahi hoti

Kuch log sochte hain: “total participation hai to E2 ko R12 mein merge kar do”. Nahi — merge sirf 1:1 (dono total) mein hota hai. M:N mein bridge table hi chahiye. Aur “multivalued A22 ko R12 ke saath ek table (A11, A21, A22)” me rakhna bhi galat design hai: A22 sirf A21 par depend karta hai, A11 par nahi — ye multivalued dependency/redundancy paida karta hai (4NF violation) aur A22 ki khaali list ko represent nahi kar paata. Isliye 4.

3.13 · Lesson 3 cheat box last-night revision

Mapping 1-liners
  • Strong → 1 table; composite → leaves; derived → none
  • Multivalued → +1 table (owner key + attr)
  • Weak → PK = owner PK + partial key
  • 1:N → FK on N-side; 1:1 → FK (UNIQUE) on total side; both total → merge
  • M:N → bridge, PK = both keys
  • Ternary → +1 table, leg “1” not in key
  • ISA → options A/B/C/D
Minimum tables formula

= strong + weak + #multivalued + #M:N + #n-ary − #(1:1 both total)

Identifying, 1:N, derived, composite = 0.

DA 2026 Q61 = 4.

Top traps
  • Total participation never adds or removes a table (except 1:1 both total merge).
  • Composite attribute: columns = leaves only.
  • Weak entity FK carries the whole owner key; bridge table to weak entity carries owner key + partial key.
  • Multivalued attribute in one cell breaks 1NF; two multivalued attributes need two tables.
  • Relationship attribute in 1:N goes to N-side; in M:N stays in bridge.
