Keys aur Integrity Constraints
Superkey, candidate, primary, alternate, foreign key; domain / entity / referential integrity; CASCADE, SET NULL, RESTRICT; keys ginna aur FDs se nikalna.

5.1 · Key ki zaroorat “exact kaunsa Rahul?”

Class mein do Rahul hain. Teacher bole: “Rahul ke marks dikhao.” Kaunse Rahul? Database ko guess nahi karna chahiye. Isliye hum aisa column (ya columns ka combination) dhoondhte hain jo har row ko alag pehchan de. Isi ko key kehte hain.

Hamara main example (poore lesson mein yahi table)

102b@gmail.comAmanD1
103c@gmail.comRahulD2
104d@gmail.comPriyaD2
Hum maan rahe hain (declared rules)
  • RollNo hamesha unique (do students ka same RollNo nahi).
  • Email hamesha unique.
  • Name repeat ho sakta hai (Rahul do baar).
  • DeptID repeat ho sakta hai.
Sabse bada rule

Sirf 4 rows dekhkar future ki uniqueness prove nahi hoti. Key schema ka declared rule / FD hai, current data ka coincidence nahi. Kal Name = Priya wala doosra student aa sakta hai.

5.2 · Superkey “pehchaan ho gayi? extra column ho to bhi chalega”

Superkey = attributes ka aisa set K jisse koi bhi do alag tuples K par same value nahi rakhte (kisi bhi valid instance mein).

t1 ≠ t2 ⇒ t1[K] ≠ t2[K]

School ka ID-card number student ko pakad leta hai. ID-card number + shirt ka rang bhi pakad leta hai — extra cheez add karne se pehchan kharab nahi hoti. Isliye superkey mein extra attributes allowed hain.

Superkey ke 3 facts
  1. Poore attributes ka set hamesha superkey hai (kyunki relation set hai ⇒ do tuples poori tarah same nahi).
  2. Superkey ka koi bhi superset bhi superkey hai.
  3. Do tuples jo K par same hain, wo ek hi tuple hain.

5.3 · Candidate key “sirf utna hi jitna zaroori”

Candidate key = minimal superkey = unique aur usme se ek bhi attribute hatane par uniqueness toot jaaye.

K candidate ⇔ K superkey  ∧  ∀ A ∈ K: K−{A} superkey nahi

Minimality test (4 step)

  1. Pehle check karo K superkey hai ya nahi. Nahi hai → khatam, candidate bhi nahi.
  2. K ka ek attribute hatao.
  3. Bacha hua set abhi bhi unique hai? Haan → hataya hua attribute extra tha → K candidate nahi.
  4. Har attribute ek-ek karke hata ke dekho. Har baar uniqueness toot jaye → K candidate key.
Shortcut: sirf ek-ek attribute hatao

Saare chhote subsets check karne ki zaroorat nahi. Agar K ka koi chhota subset superkey hota, to us subset mein attributes jodkar K se ek-kam wale subset tak jaane par wo bhi superkey hota (superkey ka superset superkey hota hai). Isliye K ka size k hai to sirf size k−1 wale subsets test karo.

Candidate keys ke 4 pakke facts

  1. Har relation mein kam se kam ek candidate key hoti hai (poore attributes ka set superkey hai; usme se jab tak extra ho hatate jao).
  2. Candidate keys alag-alag size ki ho sakti hain (RollNo = 1 attribute, (StudentID, CourseID) = 2).
  3. Ek candidate key doosri ka subset nahi hoti (warna wo minimal nahi hoti).
  4. Jo attribute kisi bhi candidate key mein aata hai use prime attribute kehte hain; baaki non-prime (Lesson 11 mein normal forms ke liye kaam aayega).
Minimal ≠ chhota naam

“Minimal” ka matlab hai koi attribute unnecessary nahi. Do alag candidate keys, ek 3 attributes ki aur ek 1 attribute ki, dono valid ho sakti hain (jab tak ek doosri ka subset na ho).

5.5 · Primary key aur Alternate key

RollNo aur Email dono candidate keys hain. Database ko ek official identifier chahiye. Jo candidate key designer chun leta hai wo primary key (PK); baaki candidate keys alternate keys.

STUDENT: RollNo = PRIMARY, Email = ALTERNATE

Primary key ke rules
  • Table mein sirf ek PRIMARY KEY constraint (par wo 2+ columns par ho sakta hai).
  • Hamesha unique + NOT NULL (entity integrity).
  • Composite PK mein har column NOT NULL.
  • PK hamesha ek candidate key hoti hai.
Alternate key ke rules
  • Alternate = candidate jo PK nahi chuni gayi.
  • Wo bhi unique + minimal hai — “doyam darja” nahi.
  • SQL mein UNIQUE (aur zaroorat ho to NOT NULL) se enforce karte hain.

Surrogate key: kabhi koi natural candidate key nahi hoti (ya bahut lambi hoti hai); tab designer ek auto-number ID (1, 2, 3, …) alag se jodta hai — ise surrogate key kehte hain, aur wahi PK banta hai.

5.6 · Foreign key ek table ka column, doosri table ki key ko point karta hai

Student ke paas sirf “D1” likha hai; department ka poora naam doosri table mein hai. Ye link hi foreign key hai: student ka DeptID → DEPARTMENT ka DeptID. Jis table mein FK hai wo child (referencing); jis table ki key ko point karti hai wo parent (referenced).

5.8 · Keys ginna GATE ka numerical favourite

R ke n attributes hain to total subsets = 2n (khali set bhi). Superkey wo subset hai jisme kam se kam ek candidate key poori ki poori aa jaye.

Rule 1 · Sirf ek candidate key (size k)

superkeys = 2n − k

Candidate key ke k attributes zaroor lene hain; baaki n−k attributes ko lo ya na lo (har ek ke 2 choice). Example: R(A,B,C,D,E) mein sirf AB key hai → 25−2 = 8.

Rule 2 · Kai candidate keys: inclusion–exclusion

Har key Ki ke liye “Ki wale subsets” = 2n−|Ki|. Fir overlap hatao: do keys ek saath = unka union wale subsets = 2n−|Ki∪Kj|.

|S1 ∪ S2| = 2n−|K1| + 2n−|K2| − 2n−|K1∪K2|

Teen keys ho to: Σ singles − Σ pairs + triple (inclusion–exclusion).

Picture: subsets ki lattice (R(A,B,C), keys A aur BC)

Lattice mein upar jaane ka matlab attribute add karna. Key ke upar ke saare nodes superkey hain. Yahan: A, BC (keys) + AB, AC, ABC = 5 superkeys. Formula check: 22 + 21 − 20 = 4 + 2 − 1 = 5 ✓.

Zyada se zyada candidate keys

n attributes ke relation mein candidate keys ek doosre ka subset nahi ho sakti (antichain). Aisi sabse badi family = sabhi middle size wale subsets:

max CKs = C(n, ⌊n/2⌋)

n=4 → 6, n=5 → 10, n=6 → 20.

Example: n = 4, 6 candidate keys

R(A,B,C,D) mein FDs: AB→CD, CD→AB, AC→BD, BD→AC, AD→BC, BC→AD. Candidate keys: AB, AC, AD, BC, BD, CD = 6 = C(4,2). Superkeys = jis subset mein koi bhi 2 attributes hon = C(4,2)+C(4,3)+C(4,4) = 6+4+1 = 11.

Ab tum try karo

R(P,Q,R,S,T) ki candidate keys sirf P aur QR hain. Superkeys kitni?

Ans: n=5. P wale: 24 = 16. QR wale: 23 = 8. Dono (PQR union): 22 = 4. Total = 16 + 8 − 4 = 20.

Ginte waqt

Superkey count mein candidate keys khud bhi shamil hain, aur khali set kabhi superkey nahi (jab tak relation mein sirf ek tuple na ho). Question mein “non-trivial / proper” likha ho to dhyaan se padho. Apne formula se hamesha ek chhote n par haath se verify kar lo.

5.9 · FDs se candidate key nikaalna chhota preview; poora Lesson 10 mein

GATE mein aksar keys FDs (functional dependencies) se nikalwate hain. Core idea: attribute set X ka closure X+ = X se jo kuch bhi FDs lagakar mil sakta hai. X superkey ⇔ X+ = saare attributes.

  1. Left-only attributes dhoondo (jo kisi FD ke right side mein kabhi nahi aate): ye har candidate key mein zaroor honge.
  2. Right-only attributes (jo sirf right side mein aate hain) kisi key mein nahi aate.
  3. Left-only attributes ka closure nikalo. Agar sab mil gaya → wahi akeli candidate key.
  4. Nahi mila to ek-ek middle attribute jodkar closure check karo (size badhate jao). Pehle jo key mil gayi, uske superset ko dobara candidate mat batao.
  5. Jo minimal sets mile wahi saari candidate keys.

Worked: R(A,B,C,D), FDs: AB → C, C → D, D → A

  • B kisi right side mein nahi → B har key mein. B+ = B (akela kaafi nahi).
  • (A,B)+: AB→C, C→D → A,B,C,D sab ✓ ⇒ AB candidate.
  • (B,C)+: C→D, D→A, phir AB→C → sab ✓ ⇒ BC candidate.
  • (B,D)+: D→A, AB→C → sab ✓ ⇒ BD candidate.
  • Candidate keys: AB, BC, BD (3 keys). Superkeys: B wale subsets jisme A, C ya D mein se kam se kam ek ho = 3 (pairs) + 3 (triples) + 1 = 7.
Aage kahan?

Closure, minimal cover, FD ka derive hona, Armstrong axioms — sab Lesson 10 mein. Yahan sirf itna yaad rakho: key nikalna = closure test + minimality. Real PYQs (2026 Q17, 2025 Q57) niche 5.14 mein hain.

5.10 · Integrity constraints galat data ko andar aane se rokne ke rules

Socho database mein RollNo duplicate, Age = −9, ya DeptID = D99 (jab D99 department hai hi nahi) insert ho jaaye — data kharab ho jayega. Aise errors rokne ke rules = integrity constraints. DBMS har INSERT/DELETE/UPDATE par inhe check karta hai; toote to operation reject.

Ek poora CREATE TABLE

CREATE TABLE Department (
  DeptID  CHAR(2) PRIMARY KEY,
  DName   VARCHAR(30) NOT NULL
);
CREATE TABLE Student (
  RollNo  INT PRIMARY KEY,                    -- key + entity integrity
  Email   VARCHAR(40) UNIQUE,                 -- alternate key
  Name    VARCHAR(40) NOT NULL,
  Age     INT CHECK (Age >= 0 AND Age <= 120),   -- domain / semantic
  DeptID  CHAR(2),                            -- nullable FK
  FOREIGN KEY (DeptID) REFERENCES Department(DeptID)   -- referential integrity
);
PRIMARY KEY vs UNIQUE
  • PK: unique + NOT NULL, table mein ek hi.
  • UNIQUE: unique, NULL allowed (standard SQL mein kai NULL alag-alag maane jaate hain), table mein kai.
  • Dono par FK point kar sakti hai.
Trap

FK lagane se column automatically NOT NULL nahi ho jaata. NOT NULL alag se likhna padta hai. Isliye “FK NULL ho sakti hai” = True (jab tak NOT NULL na ho).

Kaun sa operation kaunsa constraint tod sakta hai

Aage ki table (5.11) mein ye poori tarah tabulate hai; GATE 2026 Q26 isi par bana tha.

Cascade ke 4 traps
  1. Chain mein ek bhi RESTRICT/NO ACTION link mile to poora statement fail (kuch bhi delete nahi hota).
  2. SET NULL NOT NULL column par nahi chalta.
  3. SET DEFAULT ki default value parent mein na ho to violation.
  4. Self-referencing table mein CASCADE se poora sub-tree delete ho sakta hai (Practice Q8).
Exam recipe: “kitne tuples delete honge?”

(1) Jo row delete ho rahi hai wo gino. (2) Uske children dhoondo; har child edge ka action dekho: CASCADE → wo bhi delete, aur unke children par bhi yahi recipe; SET NULL/DEFAULT → update, delete nahi, aage nahi badhna; RESTRICT/NO ACTION → poora statement fail, answer 0. (3) Sab milakar total.

PYQ 4 · GATE DA 2025 · Q57 MSQ · Keys + BCNF

Relation R(A,B,C,D,E,F,G) with FDs: A → BCEF, E → DG, BC → A. Which is/are correct?
(A) A is the only candidate key of R
(B) A, BC are the candidate keys of R
(C) A, BC, E are the candidate keys of R
(D) Relation R is not in Boyce-Codd Normal Form (BCNF)

  1. A+: A → B,C,E,F; E → D,G ⇒ ABCDEFG (sab). A superkey, aur akela attribute hai ⇒ A candidate.
  2. BC+: BC → A, phir A se sab ⇒ sab. B akela: B+ = B; C akela: C+ = C ⇒ BC candidate (minimal).
  3. E+ = E, D, G = EDG ≠ sab ⇒ E key nahi. Koi aur key? Key mein A ya (B aur C dono) hona chahiye (sirf yahi do tareeke A tak pahunchne ke); isliye aur koi minimal key nahi. Candidate keys = {A, BC}.
  4. BCNF check (Lesson 11 ka preview): E → DG ka left side E superkey nahi (E+ sab nahi) ⇒ BCNF violate ⇒ R BCNF mein nahi.
Answer
B, D. (A) galat kyunki BC bhi key hai; (C) galat kyunki E key nahi. Is sawaal mein key aur BCNF dono ka mix hai — BCNF Lesson 11 mein detail se.

5.15 · Lesson 5 cheat box

Keys: 8 lines
  • Superkey = unique; extra OK.
  • Candidate = minimal superkey (ek bhi attribute hatao to uniqueness toote).
  • Primary = chosen candidate; unique + NOT NULL; table mein ek.
  • Alternate = unchosen candidate.
  • Composite = 2+ attributes.
  • Foreign key = reference; repeat + NULL allowed; parent ki PK/UNIQUE key ko point.
  • Key = schema-rule, sample data nahi.
  • Candidate keys ek doosri ki subset nahi; max = C(n, ⌊n/2⌋).
Counting formulas
  • 1 key (size k): 2n−k.
  • 2 keys: 2n−|K1| + 2n−|K2| − 2n−|K1∪K2|.
  • Poora set hi key: 1.
  • Har single attribute key: 2n−1.
  • X superkey ⇔ X+ = R.
  • Left-only attributes ⇒ har key mein.
  • Right-only attributes ⇒ kisi key mein nahi.
Integrity traps
  • Parent INSERT, child DELETE: kabhi referential nahi todte.
  • Child INSERT, parent DELETE: toot sakte hain.
  • FK NOT NULL nahi hoti; NULL = “kisi ko point nahi”.
  • Duplicate PK = key violation, NULL PK = entity violation, D9 jaisa FK = referential.
  • SET NULL: nullable FK chahiye; SET DEFAULT: default parent mein ho.
  • Chain mein ek RESTRICT = poora delete fail.
