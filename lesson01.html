1.1 · Database design — pehle naksha, phir ghar why ER model?

Ghar banane wali analogy

Ghar banane se pehle architect ek naksha (blueprint) banata hai: kitne kamre, kaun kaha — abhi eent-cement nahi lagta. Database mein bhi yehi hai. Seedhe table mat banao; pehle soch-samajh kar naksha banao. Is naksha ko hi ER diagram kehte hain (ER = Entity-Relationship).

  • Conceptual = “kya-kya cheezein hain aur aapas mein kaise juri hain” — computer/DBMS ki parwah nahi.
  • Logical = ab relational model ke tables (rows-columns, keys) mein badlo. ER → tables ke rules Lesson 3 mein.
  • Physical = disk par kaise rakhna (blocks, index, B+ tree).
ER model kyun pasand kiya jaata hai?
  • Client (non-technical) bhi diagram padh kar bata sakta hai ki “haan ye sahi hai”.
  • Galti shuru mein pakad mein aa jaati hai — baad mein table badalna mehnga hota hai.
  • Ek ER diagram se mechanical rules se tables ban jaati hain (Lesson 3).

1.2 · Entity, entity type, entity set teen alag shabd, teeno confusing

Class register wali picture

Class ka register socho. Register ka header (RollNo | Name | Age) ek template hai. Register ke andar likhe hue bachche asli log hain. Teeno shabd is picture se samajh aate hain:

Trap: entity vs attribute

“Name” ya “Age” entity nahi hain — ye STUDENT ki properties hain. Entity wo hai jisse hum “ek-ek karke” gin sakte hain aur jiske baare mein kai baatein store karni hon.

Ab tum try karo

Q. “COURSE” entity type hai ya entity set? Aur “DBMS (C1)”?

Answer: COURSE = entity type (rectangle mein likha jaata hai); DBMS (C1) = ek entity; agar saare courses ko ek saath bolein to entity set.

1.3 · Attribute — entity ki properties 5 alag-alag type, 1 diagram mein

Attribute = entity ke baare mein ek fact (property). Har attribute ki ek domain hoti hai (allowed values ka set; jaise Age ∈ 0..120). Agar kisi entity ke liye value maloom nahi / lagu nahi, to NULL.

Fig 1.1 — STUDENT entity ke saare attribute types ek hi diagram mein

Attribute ke 4 “jode” (har attribute inme se ek-ek mein aata hai)

JodiOption 1Option 2Test: khud se pucho
Simple / CompositeSimple (atomic): aage todne ka faayda nahi — Age, RollNoComposite: kai chhote meaningful parts mein tut-ta hai — Name = FirstName + LastName; Address = City + PIN + Street“Kya iske parts alag se kaam ke hain?” (haan = composite)
Single / Multi-valuedSingle-valued: ek entity ki ek hi value — RollNo, DOBMulti-valued: ek entity ki ek se zyada values — PhoneNo, Hobbies, Skills. Notation: double oval, set {PhoneNo}“Ek bande ke kitne ho sakte hain?” (>1 = multi)
Stored / DerivedStored: seedha database mein rakha jaata hai — DOBDerived: dusre attribute se calculate ho jaata hai — Age (from DOB), TotalMarks. Dashed oval“Kya ise dusre attribute se nikaal sakte hain?” (haan = derived)
Key / Non-keyKey: entity ko uniquely identify kare — RollNoNon-key: baaki sab“Kya do entities mein ye same ho sakta hai?” (nahi = key)
Confusion killer (GATE inhi se poochta hai)
  • Composite ≠ multivalued. Name = (First, Last) composite hai, chahe ek hi naam ho. PhoneNo = {n1, n2, n3} multivalued hai, chahe number ke parts na hon.
  • Ek attribute dono ho sakta hai: multi-valued composite, jaise Address ki list (har Address = Street+City+PIN) — notation {Address(Street, City, PIN)}.
  • Derived attribute database mein store nahi hota (store karna redundancy). ER-to-table mein ise chhod dete hain.
  • Key sirf single-valued hota hai — multivalued attribute kabhi key nahi.

Composite attribute ka matlab ek aur picture se

Name
→tootta hai
FirstNameMiddleNameLastName

Fayda: kabhi sirf LastName se search karna ho to parts alag hone se asaan. Agar kabhi sirf poora naam hi chahiye, to Name ko simple bhi rakh sakte ho — ye design decision hai (poochne wale ko question mein bata diya jaata hai).

Yaad rakhne ki trick

Multi = Many values → double oval → ER-to-table mein alag table.
Composite = Chhote parts → sub-ovals → ER-to-table mein flatten (parts hi columns bante hain).
Derived = Dotted → ER-to-table mein gayab.

Ab tum try karo

Q. STUDENT ke Name(First, Last) aur 3 phone numbers hain. Name composite hai ya multivalued? PhoneNumbers?

Answer: Name composite (parts hain, par ek hi naam); PhoneNumbers multivalued (ek student ke kai numbers). Reason: parts vs number of values — ye do alag sawaal hain.

1.4 · Keys — ER model mein pehchaan kaise? entity ko uniquely identify karna

Har entity set mein do alag entities ko pehchaanna zaroori hai (warna “kaunsa Rahul?”). Isliye entity type ka ek key attribute (ya attributes ka set) hota hai — underline se dikhate hain.

NaamDefinitionExample: EMPLOYEE(EmpID, Email, Phone, Name, Dept)
Super keyAttributes ka koi bhi set jo unique pehchaan de (extra attributes ho sakte hain){EmpID}, {EmpID, Name}, {Email}, {Email, Phone} … (agar Email, EmpID unique hain)
Candidate keyMinimal super key — koi attribute hatao to unique rehna band{EmpID}, {Email}
Primary keyCandidate keys mein se chuni hui ek (designer ka decision). ER mein underlineEmpID
Composite keyPrimary/candidate key jo ek se zyada attributes ki hoMarks(RollNo, Subject) — akela RollNo ya akela Subject unique nahi
Formal: super key kab?

Set K super key hai agar kisi do alag entities ke liye K ki values kabhi same nahi hoti. Ye ek constraint hai — sirf abhi ke data dekh kar nahi, real-world rule se tay hota hai. (Agar abhi sab ages alag hain, to Age key nahi ban jaata!)

  • Ek entity type ki kai candidate keys ho sakti hain; sab underline nahi karte — sirf primary key underline hoti hai (kuch books mein sab candidate keys).
  • Strong entity = jiski apni key ho. Weak entity = jiski apni key nahi (Lesson 3).
  • Do attributes ke saath underline karne ka matlab hai: dono milkar key hain (composite key), alag-alag nahi.
Trap

RollNo + Name dono underlined ho to iska matlab {RollNo, Name} milkar key — ye minimal nahi (RollNo akela kaafi hai), isliye design galat/redundant hai. Minimal key hi candidate key hoti hai.

Ab tum try karo

Q. Entity BOOK(ISBN, Title, Author, Edition) mein ISBN unique hai. Super keys kitni hain (sirf in 4 attributes ke subsets mein se)?

Answer: ISBN wale saare subsets = ISBN ke saath baaki 3 attributes ka koi bhi subset = 23 = 8 super keys (candidate key sirf {ISBN}).

1.5 · Chen notation ki symbol-list poori ek jagah

GATE (aur Elmasri–Navathe ki book) Chen notation use karti hai. Ye table dhyaan se padho — ek symbol bhoola to poora diagram galat padhoge.

SymbolNaamMatlab
RectangleEntity type (strong)
Double rectangleWeak entity type (Lesson 3)
OvalAttribute
Oval + underlineKey attribute
Oval + dashed underlinePartial key (weak entity ka discriminator)
Double ovalMultivalued attribute
Dashed ovalDerived attribute
DiamondRelationship type
Double diamondIdentifying relationship (weak entity ka owner se rishta)
Single linePartial participation / attribute-entity link
Double lineTotal participation (har entity zaroor)
Labels 1, N, MCardinality ratio (Lesson 2)
Dusri notations bhi hoti hain

Bahut tools mein crow's foot (UML-style) notation milti hai: rectangle mein attributes andar likhe jaate hain, aur line ke end par “kauwe ka paaon” (many) dikhta hai. Concept wahi hai; GATE mein diagram diya hoga to Chen style me hi, ya sawaal text me likha hoga.

Shapes yaad rakhne ki kahani

Rectangle = Real cheez (entity). Oval = One property (attribute). Diamond = Doori mitaane wala rishta (relationship — do cheezon ko jodta hai). Double = “extra khaas”: double oval = kai values, double rectangle = kamzor (weak), double line = zaroori (total), double diamond = identifying.

1.6 · Attribute banao ya entity? design ka sabse common sawaal

Dept ko EMPLOYEE ka attribute (“Dept = CSE” text) banaye ya alag DEPARTMENT entity?

Option A: Dept = sirf ek attribute
Option B: DEPARTMENT alag entity + WORKS_IN relationship
Agar …To banaoKyun?

Cheez kai logon se share hoti hai (ek Dept mein 100 employees)EntityText har employee ke saath repeat hoga = redundancy, typo se inconsistency

Trap: foreign key ko attribute mat banao

ER diagram mein “DeptID” ko EMPLOYEE ka attribute likhna galat design hai — ye relational (table) level ki cheez hai. ER mein DEPARTMENT entity + WORKS_IN relationship banao; foreign key khud tables banate waqt aayegi (Lesson 3).

Ab tum try karo

Q. Student ka “Hostel” (naam, warden, rooms) attribute banaye ya entity?

Answer: Entity — usse apne attributes hain (warden, rooms) aur ek hostel mein kai students rehte hain (share hota hai).

1.7 · Poora example — Library ka ER requirement se diagram tak

Requirement (client ki zubaan mein): “Library mein members hote hain, har member ka ID, naam aur kai phone numbers. Books hoti hain jinka ISBN, title, price aur ek ya zyada authors. Member books borrow karta hai, har borrow ki issue date save honi chahiye.”

Teen aasan steps

  1. Noun (sangya) dhundo → entity ya attribute. member, book = entities (inhe ek-ek karke gin sakte hain). ID, naam, phone, ISBN, title, price, author = attributes.
  2. Verb (kriya) dhundo → relationship. “borrows” = MEMBER aur BOOK ke beech relationship.
  3. Type tay karo. Phone (kai) = multivalued; Author (“ek ya zyada”) = multivalued; MemberID, ISBN = key; IssueDate = relationship ka attribute (kyunki ye “is member ne is book ko kab liya” — dono par depend).
Fig 1.2 — Library ER (M:N BORROWS, Lesson 2 mein cardinality detail)
Iska relational form kaisa banega? (preview)

MEMBER(MemberID, Name) + MEMBER_PHONE(MemberID, Phone) + BOOK(ISBN, Title, Price) + BOOK_AUTHOR(ISBN, Author) + BORROWS(MemberID, ISBN, IssueDate) → 5 tables. (Dekho kaise multivalued & M:N alag tables bane. Rules Lesson 3 mein.)

BORROWS ka key?

Agar ek member ek hi book ko dobara issue kar sakta hai (alag date par), to (MemberID, ISBN) unique nahi rahega; tab IssueDate bhi key mein ya naya BorrowID. Ye business rule par depend karta hai — question mein jo diya ho wahi maano.

1.8 · Counting: ek entity ke kitne columns? Lesson 3 ka warm-up

Ek entity type ko table mein badalne par kitne columns bante hain, ye GATE ka typical numerical hai. Teen rules:

Attribute typeTable mein kya hota hai?Columns
Simple, single-valuedSeedha ek column1
CompositeFlatten: sirf sub-parts columns banenge (composite khud nahi)= parts ki ginti (agar part bhi composite hai to uske parts)
DerivedStore nahi hota0
MultivaluedMain table mein nahi; alag table (owner ki key + wo attribute) banti hai0 main table mein (+1 nayi table)

Worked example

STUDENT(RollNo, Name(First, Middle, Last), DOB, /Age, Address(City, PIN), {Phone}, {Skill})

  1. Simple: RollNo, DOB → 2
  2. Composite flatten: Name → First, Middle, Last = 3; Address → City, PIN = 2
  3. Derived /Age → 0
  4. Multivalued {Phone}, {Skill} → 0 in main table, par 2 extra tables: STUDENT_PHONE(RollNo, Phone), STUDENT_SKILL(RollNo, Skill)

Main table STUDENT: 2 + 3 + 2 = 7 columns  →  STUDENT(RollNo, First, Middle, Last, DOB, City, PIN). Total tables = 3.

Trap

Composite attribute khud ko column mat gino (Name + First + Last = galat, 4). Sirf leaf (sabse neeche waale) parts column bante hain.

1.9 · PYQ kahan hain? 2024-2026 ke teeno papers ka scan

GATE DA 2024, 2025 aur 2026 ke teeno papers mein sirf ek ER-model question hai: DA 2026 Q61 (NAT, 2 marks) — ER diagram mein multivalued attribute + M:N relationship ko 3NF relations mein badalna. Ye Lesson 3 ke mapping rules par poora tika hai, isliye uska full solution Lesson 3.10 mein diya hai. Lesson 1 se jo tumhe chahiye wo hai: “A22 multivalued hai” ka matlab (double oval → alag table).

Strategy

ER sawaal GATE DA mein kam aate hain par pakki marks hote hain (1 question = 2 marks NAT, koi guess nahi). Notation + mapping rules ek baar achhe se pakad lo — 15 minute ka kaam, 2 marks ki guarantee.

1.10 · Practice questions pehle khud solve, phir jawab dekho

Q1. Ek GATE-type: ek relation mein “Age” DOB se calculate hota hai. ER mein ise kaise dikhayenge, aur table mein?
✔ Dashed (derived) oval; table mein store nahi (0 column).
Derived attribute redundancy hai; jab zarurat ho query mein CURRENT_DATE - DOB se nikaal lete hain.
Q2. EMPLOYEE(EmpID, Name(First, Last), {Skills}, Salary, /Experience). Main table kitne columns? Kitni total tables?
✔ Main table: EmpID, First, Last, Salary = 4 columns; total tables = 2 (EMPLOYEE + EMP_SKILLS).
Experience derived (0). Skills multivalued (alag table).
Q3. Kaunsa sahi hai? (A) Composite = multivalued (B) Ek attribute composite aur multivalued dono ho sakta hai (C) Key attribute multivalued ho sakta hai (D) Derived attribute store hota hai.
✔ (B)
Jaise {Address(Street, City, PIN)}. (C) galat: key single-valued hoti hai. (D) galat.
Q4. Entity type, entity aur entity set mein se “Rahul (RollNo 101)” kya hai?
✔ Entity
STUDENT = entity type; saare current students = entity set.
Q5. BOOK(ISBN, Title, Author, Edition). ISBN unique hai. Title+Edition bhi unique hai (assume). Candidate keys kya hain? Kitne super keys?
✔ Candidate keys: {ISBN}, {Title, Edition}. Super keys = 23 (ISBN wale) + (Title,Edition wale: baaki 2 attributes ISBN, Author ke 4 subsets, jisme ISBN wale already gine = ISBN-rahit 2 subsets: {}, {Author}) = 8 + 2 = 10.
ISBN-wale subsets: 23=8. ISBN-rahit jo {Title,Edition} contain karte hain: {T,E}, {T,E,A} = 2. Total 10.
Q6. Hostel Warden ko STUDENT ka attribute likha jaye ya entity? Kab?
✔ Agar warden ke apne attributes (phone, name, office) hain aur kai students ka ek warden hai to entity.
Sharing + own attributes = entity.
Q7. STUDENT entity ke attributes: RollNo, Name(F,L), Phones(set), DOB, Age(derived). Table mein attribute-columns ki ginti?
✔ RollNo, F, L, DOB = 4
Phones alag table; Age drop.
Q8. {Address(Street, City, PIN)} ko table mein kaise?
✔ Alag table: ADDRESS(OwnerKey, Street, City, PIN) — kyunki multivalued; composite hone ke karan Street, City, PIN teeno columns.
Key = (OwnerKey + sab address parts) agar koi aur discriminator nahi.
Q9. True/False: Do alag entity sets ke attributes ke naam same ho sakte hain. Do alag entities ki same key value ho sakti hai?
✔ Pehla: True (STUDENT.Name, COURSE.Name). Dusra: same entity set mein False; alag entity sets mein True.
Key uniqueness sirf apne entity set ke andar.
Q10. Ek ER diagram mein 4 entity types (har ek strong), 3 multivalued attributes, koi relationship nahi. Minimum tables?
✔ 7
4 + 3.

1.11 · Lesson 1 cheat box last-night revision

Notation
  • Rectangle = entity; double rectangle = weak entity
  • Oval = attribute; underline = key; dashed underline = partial key
  • Double oval = multivalued; dashed oval = derived; sub-ovals = composite
  • Diamond = relationship; double diamond = identifying
  • Double line = total participation
Counting rules (table columns)
  • Simple: +1; composite: leaf parts only; derived: 0; multivalued: 0 in main table, +1 table
  • Key attribute never multivalued
  • Multivalued composite → own table with all parts
Top traps
  • Composite ≠ multivalued (parts vs count of values).
  • Derived attributes are not stored.
  • FK is a table-level idea; do not draw DeptID as an attribute in ER.
  • Entity type (rectangle) ≠ entity (one row) ≠ entity set (all rows now).
